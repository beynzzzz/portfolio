PROJECT 01 / HOMELAB

Odysseus

My self-hosted Debian server, built as a practical environment for learning Linux, networking, Docker, monitoring, automation and security.

Debian Docker Caddy Cloudflare WireGuard Git Bash

01 / BACKGROUND

Why I built it

I wanted somewhere I could work with infrastructure myself instead of only learning concepts in theory.

Odysseus started as a Debian installation on a mini PC and gradually became the main environment I use for experimenting with Linux, Docker, networking and self-hosted services.

I deliberately kept adding things as I found a reason to use them. The aim wasn't to install as many applications as possible. I wanted each service to give me something useful while also teaching me how the underlying system worked.

02 / HOST

The server itself

Odysseus runs Debian Linux directly on the mini PC. Docker is used for most application services, while Linux itself handles the host, networking, storage, services and access to the machine.

Debian

The base operating system. I use it to manage the filesystem, users, permissions, networking, services and Docker runtime.

Docker

Most applications run as containers. Docker Compose keeps each service configuration separate and makes the deployments easier to reproduce and maintain.

Persistent storage

Services that need to retain data use Docker volumes or bind-mounted directories so that container recreation does not remove application data.

Docker networking

Containers that need to communicate with each other use defined Docker networks rather than exposing every service directly to the host or internet.

03 / NETWORKING

How traffic reaches the server

The public portfolio and the private administration side of the homelab are treated differently.

Public portfolio

Visitors connect to Cloudflare first. A Cloudflare Tunnel carries the request back to the cloudflared container running on Odysseus. Caddy then serves the static website. 

Browser
  -> Cloudflare
  -> Cloudflare Tunnel
  -> cloudflared
  -> Caddy
  -> /srv/www/portfolio

Private services

Administrative services are not published in the same way as the portfolio. My Homepage dashboard and management interfaces are accessed from trusted network connections or through WireGuard.

This keeps the public-facing part of the server separate from the interfaces I use to manage the homelab.

04 / SERVICES

What I currently run

Caddy

Handles HTTPS and reverse proxying for web services. It also manages certificates for the domains I host.

Cloudflared

Maintains the Cloudflare Tunnel used by the public portfolio. The connection is initiated outbound from Odysseus, so I do not need to forward web ports from the router.

WireGuard

Provides VPN access when I need to reach private homelab services remotely.

Vaultwarden

Self-hosted password manager. This is one of the services where backups, access control and careful updates matter most.

AdGuard Home

Provides DNS filtering for the network and gives me practical experience working with DNS and local name resolution.

Homepage

My private dashboard for accessing services and viewing basic container resource usage.

Grafana

Used for visualising server and container metrics and giving me a better view of what Odysseus is doing over time.

Uptime Kuma

Monitors service availability so I can see when something becomes unavailable or behaves unexpectedly.

Diun

Watches the Docker images I use and sends notifications when newer images are available.

05 / SECURITY

Decisions I made around security

Security has mostly been about reducing what is exposed and avoiding giving individual services more access than they need.

No web port forwarding

I originally looked at publishing the portfolio through the normal HTTPS path, but switched to Cloudflare Tunnel instead. The public site now works without forwarding ports 80 or 443 from my router to the server.

Public and private separation

The portfolio is public, while the Homepage dashboard and administrative services stay on the trusted side of the environment.

Read-only website mount

Caddy serves the production portfolio from /srv/www/portfolio using a read-only mount. The live site is not served directly from the Git repository.

Secrets outside Git

API tokens, private keys and environment files are kept out of the public repository. Changes are reviewed before they are pushed to GitHub.

Restricted Git access

Odysseus uses a dedicated SSH deploy key for the portfolio repository rather than a credential with broad access to my GitHub account.

Security headers

Caddy adds browser security headers to the public site, including a restrictive Content Security Policy and protections against framing and content-type sniffing.

06 / VERSION CONTROL

How I manage changes

The development version of the portfolio lives in a Git repository under my home directory on Odysseus.

Git workflow

I edit the site in the working repository, review the changes with Git, then create a commit once I am happy with the result. The commits are pushed to the public GitHub repository.

This gives me a history of the project rather than just having one copy of the finished website.

07 / DEPLOYMENT

Publishing the website

GitHub is used for version control, but the website itself is hosted on Odysseus.

Bash deployment script

I wrote a Bash script to handle deployment rather than manually copying files every time the site changes.

Before deployment it checks the state of the Git repository and creates a copy of the currently deployed site.

It then copies only the files that are supposed to be public into /srv/www/portfolio.

Once deployment finishes, the script checks the live site. If the health check fails, the previous version can be restored.

08 / TROUBLESHOOTING

Things that did not work first time

Some of the most useful parts of the project came from working out why something wasn't behaving as expected.

Cloudflare 522

My first attempt at making the portfolio public resulted in a Cloudflare 522 timeout.

The browser could reach Cloudflare, but Cloudflare could not establish the connection back to Caddy.

Instead of opening HTTPS on the router, I changed the design and introduced Cloudflare Tunnel.

Caddy certificate failure

When I first added the new domain, Caddy attempted the normal HTTP and TLS certificate challenges and failed.

The Caddy logs showed that the new site was missing the Cloudflare DNS challenge configuration already used by my other services.

After applying the existing DNS challenge configuration, Caddy was able to obtain the certificate correctly.

Container updates

I initially updated containers manually without much of a standard process.

I now check the running state first, keep rollback options where appropriate, pull the new image and verify the service afterwards.

Development vs production

The first version of the portfolio existed only in the Git working directory.

I separated the production files into /srv/www/portfolio so Caddy does not expose Git metadata or development files.

09 / WHAT I LEARNED

What this project gave me

The main benefit has been seeing how technologies that I previously thought about separately actually interact with each other.

DNS affects how a request finds the server. Cloudflare sits in front of it. The tunnel carries the request to Docker. Caddy decides what should receive it. Linux and Docker networking move the traffic between services, and the application eventually responds.

I also became much more comfortable checking logs and working backwards through a problem instead of immediately changing configuration.

My next step is to build a disposable Linux environment where I can deliberately break these components and learn the underlying system in more depth without affecting Odysseus.
